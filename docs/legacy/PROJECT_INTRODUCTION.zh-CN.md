# Journey Risk Pricing & Recovery Agent —— 项目介绍

[English](./PROJECT_INTRODUCTION.md) | **简体中文**

*阿里云 x Atlas Agentic AI Hackathon 参赛作品的评审向介绍。环境搭建、命令与工程结构请见 [README](../README.zh-CN.md)。*

## 1. 问题 —— 以及它背后的现场证据

OTP（准点率）告诉行业航班晚点的频率，却无法为**某一条具体行程**定价——而且中断从来不只是误机。风暴会放大延误方差，空域关闭会迫使绕航，载量限制会把旅客请下飞机。这些风险在起飞前都没有价格，行业手里只有事后统计与法定补偿表。

其中最尖锐的实例是中转本身：一条国际中转可以在名义上合法——满足公布的最短中转时间——却在实际执行中失败，因为入境审查、行李提取、重新托运、安检和航站楼换乘会吃光全部缓冲。旅客只有在已经误机的那一刻才发现这个风险，而那恰恰是成本最昂贵的时刻。

本项目源于同一命题的两次亲历观察，一次来自柜台的一侧，一次来自另一侧（已匿名化；完整记述见 [PROJECT_CONTEXT.md — Field evidence](PROJECT_CONTEXT.md)）：

- **观察 1 —— 迟到定价的代价。** 一位旅客接受了航司推荐的 **100 分钟**国际转国内西雅图中转，两端客服都说没问题。实际入境审查耗时近两小时，中转失败，旅客在**没有酒店安置**的情况下等待了约 **15 小时**。一份从未被任何人定价的风险——事后结算的期望成本约为 **$340**——而一次提前干预只需约 **$80**。
- **观察 2 —— 提前定价的样子。** 回程时，空域关闭迫使改航，改航又带来载量与油量限制。同一家航司面对*自己的*问题时行为截然相反：它提前量化了风险，用逐级升档的 **$200 / $500 / $900** 激励阶梯购买志愿者（该项目的真实上限案例是一张 $2,000 代金券），以最小代价化解了问题。

**焊接点：** 航司早就懂得为自己的问题提前定价，只是从不用同样的方法对待旅客的问题——而且它们只为自己的运营风险定价，从不为旅客的中转或天气敞口定价。这个产品要闭合的就是这种不对称：**一个定价引擎，覆盖每一类风险域，服务柜台两侧。**一个论点：**“风险越早被看见，就越便宜。”**

## 2. 解决方案 —— 一个定价引擎，两种翻译

**Journey Risk Pricing（行程风险定价）**把行程拆解为可定价的风险域，在中断结算之前报出保护成本。本演示中引擎为三个风险域定价：**C1 中转脆弱性**、**C2 天气方差**、**C5/C6 空域关闭与载量限制**。**Connection Confidence（连接置信度）**——赶上中转的概率，按行程逐一计算，由可解释的因子构成，并带有显式的不确定性带宽——是第一个风险域的头牌指标，而不是整个产品。

引擎使用的是金融风险定价的语言：

| 金融概念 | 航空映射 | 演示中的落点 |
| --- | --- | --- |
| 承保（风险域） | 行程被拆解为可定价的中断风险：中转、天气、运营 | T2 因子瀑布图、C2 面板、运营端志愿者面板 |
| 期望损失定价（`PD × LGD`） | 期望中断成本 = `P(中断) × (改签 + 酒店 + 餐食 + 服务人力 + 商誉)` | 运营端成本对比：预期 $340 vs 主动 $80 |
| Mark-to-market 重定价 | 新证据实时重估行程：风暴预报把置信度从 92% 压到 34%，保护报价随之移动 | C2 重定价面板 |
| 风险转移经济学 | 期望中断成本 vs 航司出资的主动保护成本（$340 vs $80）；志愿者阶梯 = 对“灵活性”的市场化询价 | T2 成本对 callout、O2 激励阶梯 |

同一个模型在两侧被翻译成不同的语言：

- 对**旅客**：置信度评分、背后的驱动因子，以及基于明确同意的保护与恢复方案。
- 对**航司**：期望中断成本——在演示中实例化为期望误机成本 `P(误机) × (改签 + 酒店 + 餐食 + 服务人力 + 商誉)`——并与提前行动的成本对比。

这种平衡由四个机制保证，全部在演示中可见：

1. **干预阈值。** 只有当期望中断成本超过主动干预成本时，才建议提前干预；两者的对比记录在审计轨迹中（演示中为 $340 vs $80）。
2. **成本阶梯 L0–L4。** 干预从最便宜的足够档位逐级升档：L0 风险披露（免费、必给）→ L1 自愿当日改签（免差价）→ L2 定向志愿者激励 → L3 含酒店承诺的保护性改签 → L4 事后误机处置（最贵，尽量避免）。
3. **双边排序。** 恢复方案按旅客选择的优先级（到达时间、避免过夜、成本）排序，航司边际成本（越空的航班填座越便宜）作为可见的第二维展示——权衡被摊开，而不是被隐藏。
4. **航司出资的主动保护。** 演示定价的是*是否干预的决策*，而不是旅客付费产品：主动保护由航司出资，因为它比所避免的误机更便宜。本 demo 不出售任何旅客保费；一份定价保护产品需要什么，见 §8。

## 3. 为什么是 Agentic —— 感知-翻译层，以及 Agent 绝不能做什么

风险定价是一条链：异构的非结构化证据必须变成结构化的风险因子，因子必须变成价格，价格必须变成双方都同意的行动。

```text
非结构化证据                结构化风险因子                 价格与行动
(气象通告、NOTAM、     -->  (到达航班波、风暴因子、    -->  (置信度、中断成本、
 空域通告、机场流程          期望耗时±方差，                 优先级驱动的恢复排序、
 报告、旅客间相互            每一项都带来源标注)              同意闸门、审计)
 矛盾的评价)
        ↑                              ↑                                   ↑
   Agent 感知层                确定性定价引擎              Agent 表达层 +
   (读取、抽取、               (不讲自然语言，               引擎执行
    标注来源)                   全程可审计)
```

中断风险的证据天然是文本与人类报告，而不是干净的特征。Agent 就是读取证据、将其转化为可定价输入的那一层；引擎负责定价；随后 Agent 解释价格、协商行动。有一条边界永不移动：**Agent 只负责理解与表达；排序、执行与同意确认属于确定性引擎。**

**为什么不直接复用航司收益管理（RM）？** RM 为*需求*风险定价，目标是航司收益最大化，吃的是私有预订曲线数据，既不面向旅客解释也不征求同意。我们的问题是为柜台两侧的*中断*风险定价。RM 不是替代方案，而是先例：它证明航司有能力运转一台风险定价机器；我们把同样的纪律延伸到 RM 忽视的那种风险上，并把 RM 的输出（客座率、票价）作为我们的输入。

**为什么不用纯数据驱动的 ML 模型？**（1）行程级中断结果拿不到标注数据——OTP 只有航班级且是事后统计。（2）一个要旅客付费、要航司行动的价格，必须逐因子可解释、全程可审计，黑盒承担不起同意确认。（3）预测不是稀缺资源，翻译才是。把一个概率变成被理解的价格、被同意的行动，需要语言、推理与协商——这正是 LLM 的主场。

这条链在演示中的落点：

- **C2 —— 端到端的感知。** 面板展示完整证据链：气象通告原文 → Agent 解读 → 结构化风暴因子（期望耗时、重尾区间、来源标注）→ 引擎把行程从 92% 重估到 34%。
- **T2/T4 —— 因子与理由。** 每个风险因子都带来源标注（含 *Agent estimate*）；`AgentProvider.explainOptions` 生成的逐方案解释只能引用输入给它的结构化字段——不能虚构航班、时间或价格。
- **T3 —— 协商。** 旅客输入“我今晚就想赶到，不要住酒店”，`AgentProvider.parsePreference` 返回三种结构化优先级之一，恢复方案列表随之可见地重新排序。

每次 Agent 调用都返回结构化 JSON，经白名单校验，并带模型名进入审计轨迹。失败时降级为手动按钮和隐藏的理由区块——演示永不中断。

## 4. 架构与技术亮点

五个 Provider 接口（`src/domain/types.ts`），在 `src/providers/index.ts` 中装配；组件从不直接接触任何供应商 API：

| Provider | 职责 | 实现 |
| --- | --- | --- |
| `AtlasFlightProvider` | 航班搜索 / 订座 | `mock-atlas.ts`（fixtures）· `sandbox-atlas.ts`（ATRIP REST） |
| `ConnectionRiskProvider` | 因子求和置信度模型（方差 + 正态 CDF） | `risk.ts` |
| `RecoveryProvider` | 优先级驱动的双边排序 | `recovery.ts` |
| `AuditProvider` | input → evidence → recommendation → consent → action → result | `audit.ts` |
| `AgentProvider` | 偏好解析 + 理由/通告解读生成 | `mock-agent.ts` · OpenAI 兼容 live agent |

技术亮点：

- **两个凭证安全的 dev 代理**（`vite.config.ts`）：`/api/atlas/*` 转发到 Atlas Sandbox，`/api/agent/chat` 转发到 DashScope，密钥均在服务端注入，永远不进浏览器 bundle。Agent 代理还对请求体做白名单过滤，并在服务端强制覆盖模型。
- **每个数字都有来源标注** —— *Atlas flight data*、*Estimated transfer process*、*Agent estimate*、*Agent-generated*、*Sandbox action* / *Demo simulation*。虚构数据永远不会伪装成 Atlas 数据。
- **安全失败。** 凭证缺失或上游错误时，回退到带标签的 fixtures 并显示横幅；风险与恢复工作流始终可用。
- **单一会话完成闭环。** `src/state/session.tsx` 是唯一的事实源，也是唯一的审计写入口。旅客在 T5 批准后，运营看板的西雅图行翻转为 **Protected** 并显示避免的成本——双边故事一键闭合。

## 5. 双边演示（3 分钟脚本）

全程可在零凭证的 mock 模式下运行；配置 Sandbox 凭证后，实时 Atlas 面板自动激活。

| 时间 | 节拍 | 屏幕 |
| --- | --- | --- |
| 0:00 | 钩子：匿名化的西雅图误机经历——合法的 100 分钟，损失的 15 小时 | — |
| 0:20 | 引擎为中转风险域定价：高风险，主导因子是到达航班波（09:00–09:40 三架宽体机），展示不确定性 | T1 → T2 |
| 0:50 | 旅客用自然语言表达诉求，Agent 完成解析 | T3 |
| 1:10 | 恢复方案按旅客优先级重新排序；PVG→SIN 实时 Atlas 面板展示真实 Sandbox 报价 | T4 |
| 1:50 | 明确勾选 + 批准 → 带标签的结果 → 完整审计时间线 | T5 |
| 2:20 | 运营视图：西雅图行翻转为 Protected——预期中断成本 $340 vs 主动 $80，避免 $260；志愿者阶梯是对“灵活性”的市场化询价 | O1, O2 |
| 2:45 | C2：mark-to-market——Agent 将风暴通告解读为定价因子，引擎把行程从 92% 重估至 34%；保护在风暴来临之前被定价，而不是之后 | C2 |

数据双轨：西雅图故事运行在明确标注的 fixtures 上（Atlas Sandbox 仅持有亚太库存）；实时轨道对真实 Sandbox 搜索 PVG → SIN。

## 6. 集成点

- **Atlas（ATRIP REST API）**—— 真实的航班零售与服务层。已在真实 Sandbox 上验证：`search.do` 返回含 `fid` / `routingIdentifier` / 价格的报价；静态 `x-atlas-client-id` / `x-atlas-client-secret` 鉴权；10 QPS 限流并带 `retryAfter`。在原生改签能力确认之前，改签被表达为“预订恢复方案 + 模拟原票作废”。契约详见 [ATLAS_INTEGRATION.md](../ATLAS_INTEGRATION.md)。
- **OpenAI 兼容 Agent Provider（DeepSeek 或阿里云百炼 / DashScope）**—— Agent 层，经 dev proxy 调用。结构化 JSON 输出，固定 seed 保证演示可复现，带超时与优雅降级。第三个独立的 Try an itinerary 试用台服务于用户自选行程，不改变面向评审的双边演示主线。

## 7. 可行性与落地路径

经济账本身就是论证：航班中断每年让航司损失约 **$25B–35B（约 5% 的收入）**，而本演示中的每一次干预都比它所避免的误机更便宜。构建刻意保持最小化 —— Vite + React + TypeScript，无 UI 库，除两个 dev 代理外没有后端——这正是个人参赛者在一周内能够交付、维护并完成录制的体量。

落地路径：待 Sandbox 服务能力确认后接入真实的 `verify.do`/`order.do`/`pay.do`；用实时机场流程数据源替代标注估算；为新的风险域定价——C3（航司可控运营）、C4（空管容量）、C7、C8；旅客付费的保护产品只在有持牌承保支撑之后才做（§8）。非目标保持非目标：不保证结果、不推断敏感信息、未经同意绝不行动。

## 8. 商业边界 —— 本演示不决定什么

本演示是一个**早期风险干预的决策原型**——在中断发生之前发现、解释并协调行程风险。它不是一个可销售的保险或保障产品，也不假装是。

- **不出售任何旅客保费。** 演示中的每一次干预都由航司出资：`$80` 是航司的*主动保护成本*，与 `$340` 的*期望中断成本*对比。演示定价的是「是否干预」的决策——把航司的成本改称“保费”不是在描述一个产品，而是在凭空编造一个。
- **旅客付费的保护产品需要什么** —— 均刻意不在本演示范围内：持牌承保人与付费方、明确的保障范围与权益、退款与理赔规则、承保边界，以及对风险差异化定价的公平性审查。
- **志愿者阶梯只是决策支持。** 运营端看到的是对“灵活性”的市场化询价；报价只通过运营人员的显式操作发出，旅客始终自己决定是否接受。
- **候选商业模式保持开放。** 航司出资的主动改签（演示所展示的）、OTA 售卖的航延险、旅客付费的稳定性权益，三者的付费方、定价权与承保责任各不相同。演示对它们保持中立：它定价的是风险本身，商业形态留给承担承保责任的一方去决定。
